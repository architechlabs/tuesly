# 0.2.14: keypad synchronization and native startup preferences

## Behavior

- Consume authenticated OnOff, Lightness and CTL Temperature status messages
  immediately. Route a shared bearer's replies to the matching saved node.
- Read each lighting model's publication settings. Preserve existing keypad or
  controller publication destinations. Receive ordinary group publications for
  discovered groups; virtual-address publications require label UUID support
  and remain on polling fallback.
- Where publication is unassigned, request change notifications to HA's mesh
  unicast address, and check the configuration response. Device firmware must
  actually publish status when its state changes for immediate updates.
- Reconcile every `max(5, 2 * saved_node_count)` seconds, instead of the previous
  minimum 30 seconds. This is a scheduling interval, not a response-time SLA:
  radio contention, transitions and disconnected devices can extend latency.
  User commands retain priority over reconciliation. Notifications do not reset
  reconciliation timers or mark an incomplete/offline node healthy.
- Configure Generic OnPowerUp to Restore (2) by default when both required
  native models are advertised. Read and acknowledge the device setting.
  Expose **Power-on behavior** on supported, confirmed devices: Restore previous,
  Off, or On (device defaults). Save an explicit user selection only after the
  device confirms it. Unsupported preferences do not prevent normal controls.
- Bound optional preference/publication work and retain normal controls if it
  times out. Keep mesh keys, addressing, sequence persistence and provisioning
  recovery unchanged. No ESP32 firmware changes are required.

## Native persistence and physical limits

Restoring inside HA after reconnection cannot prevent a startup flash. This
release configures the driver's own persistence rather than replaying cached
commands after boot. Bluetooth Mesh defines Restore as restoring the previous
state (or the target if powered down during a transition). Actual persistence
and electrical startup behavior must be confirmed on each driver firmware
family with a physical mains cycle. A successful acknowledgement is not proof
of flash-free output or correct nonvolatile storage implementation.

The existing SIG light is a white/tunable-white device. This change does not
claim RGB hue/saturation support for hardware that does not expose it.

## Deployment and acceptance

Version 0.2.14 is prepared locally. Python module changes require a Home
Assistant Core restart to load; reloading an integration does not reload its
Python modules. Respect the existing instruction prohibiting HA restarts:
do not activate this release without a newly authorized maintenance restart.
Keep the previous integration backup available. Do not reset or reprovision
lights for this update.

After activation, verify physical keypad on/off, dimming and white-temperature
changes against HA; then test Off -> mains off/on and a dimmed/tuned On -> mains
off/on. Confirm the preference remains after HA and driver restarts. Observe
driver output for any startup flash; do not certify flicker-free operation from
HA state alone. These hardware checks have not yet been performed for 0.2.14.
